# Durable, scoped content deletion

The general-chat regression had several interacting causes: database deletions left server RAM snapshots intact; global/group messages were broadcast and acknowledged under temporary IDs before persistence; clients optimistically hid content while sending both socket and REST deletes; and the old REST handler guessed among three message tables, allowing equal numeric IDs to select a different conversation type. REST deletion also used a legacy token-only check instead of the shared session authenticator. Append-only global delta refresh could retain deletions missed while the view was unmounted.

`contentDeletion` is now the single implementation behind REST and socket message, post and comment deletion. IDs and message types are explicit. Temporary IDs and missing types fail visibly. Only the author or an authorized administrator can delete; a DM receiver cannot erase the other person's message. The actor is checked against current database data. Post/like/comment removal, reply-reference cleanup and applicable mention/notification cleanup commit atomically. Failure rolls back without publishing success, invalidating valid cache data or deleting files. Local uploaded-file cleanup is best effort after commit. Repeated deletion is idempotent.

Global/group sends persist before broadcasting or acknowledging, so published messages have durable IDs. Successful deletion invalidates the appropriate RAM room. Version checks prevent reads begun before a write from refilling the cache with older data. Appending to an invalidated/unknown room does not create a misleading partial history snapshot. Global chat clearing and group deletion invalidate cache after persistence; the administrator post-purge endpoint uses the same deletion service.

Clients use one acknowledged REST request, with session-aware headers, in-flight coalescing, timeout/error handling and no premature removal. Typed deletion records protect global/private/group messages, feed/profile posts, mini widgets and comments against late snapshots and same-number IDs from another content type. Socket events and BroadcastChannel synchronize connected devices/tabs. Remaining quoted references and relevant media/reply overlays are cleared. Re-entry/reconnect reloads current snapshots in the main/mini global chat, group messages, feed and profile. An inactive/disconnected browser cannot know about remote changes until it reconnects; it then refreshes the authoritative snapshot.

Feed comment creation also uses a single REST write and renders the persisted comment instead of a fabricated optimistic numeric ID. This eliminates the two socket-plus-REST duplicate-creation paths, makes pending comments impossible to falsely "delete", and deduplicates the server event/response by persisted ID.

Validation:

- Six `test:deletion` groups: author/admin permissions; equal-ID table isolation; durable removal and quoted replies; cache invalidation/version/partial-history protection; database-trigger rollback and file/event ordering; session-based REST authentication; shared socket behavior; durable send IDs and failed writes; late client snapshots and comment/post ID separation.
- `test:deletion:browser` at desktop and touch/mobile widths: real GlobalChat/Feed components with two sessions, warmed RAM, author/admin deletion, peer update, reload, tab re-entry, a new message after deletion, failed REST retention, one-write comment creation/deletion, persistent post deletion and a pre-delete feed response released after the deletion event.
- Existing ten DM tests, three mention test groups and three social-navigation test groups; desktop/mobile DM, social-navigation and mention browser suites; TypeScript and production build.

Fixtures use isolated in-memory databases and controlled users/transports. No production messages were read or removed while validating the change. Deployment needs the normal build/restart, with no destructive database migration. It does not infer historical delete intent from content text or bulk-remove older duplicate rows.
